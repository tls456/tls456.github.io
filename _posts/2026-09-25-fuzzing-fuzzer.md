## Fuzzing

### 정의

**퍼징(Fuzzing)**: 프로그램에 다양한 입력을 자동으로 생성하거나 변형하여 반복적으로 전달하고,  
실행 중 오류를 찾는 동적 테스트 기법

예시: 파일을 읽는 프로그램에는 내용이 비어 있는 파일, 일부가 잘린 파일, 평소와 다른 길이나 값을 가진 파일을 전달  
정상적인 입력도 사용하며, 문법은 올바르지만 개발자가 예상하지 못한 값의 조합도 검사 대상이 된다.

일반적인 단위 테스트에서는 개발자가 특정 입력과 기대 결과를 직접 작성한다.  
퍼징에서는 검사할 함수와 실패 조건을 정한 뒤, 도구가 많은 입력을 탐색한다.  
따라서 사람이 작성한 테스트를 보완하는 데 유용하며, 프로그램이 안전하다는 것을 증명하는 방법은 아니다. -->

### 동작 원리

대표적인 **커버리지 유도 퍼징(Coverage-guided fuzzing)**은 실행한 코드에 대한 정보를 피드백으로 활용한다.  
새로운 코드 영역을 실행한 입력을 남겨 두고, 그 입력에서 다시 여러 변형을 만드는 방식이다.
> **커버리지(Coverage)**: 테스트 실행 중 프로그램의 어떤 코드 영역이나 실행 경로가 수행되었는지를 나타내는 정보

![코퍼스에서 선택한 입력을 변형해 하네스로 실행하고, 새로운 커버리지는 코퍼스에 반영하며 오류 입력은 별도로 저장하는 반복 구조](/assets/images/fuzzing-fuzzer/01-feedback-loop.svg)  
코퍼스에서 선택한 입력을 변형해 하네스로 실행하고,  
새로운 커버리지는 코퍼스에 반영하며 오류 입력은 별도로 저장하는 반복 구조
> **코퍼스(Corpus)**: 퍼징 과정에서 테스트에 사용하는 입력들의 집합

그림에서 파란 경로는 다음 탐색에 사용할 입력을 고르는 과정이고, 주황색 영역은 오류 여부를 판단하는 과정이다.  
새로운 코드를 실행했다는 사실과 오류가 발생했다는 사실은 별개이다.

1. **초기 입력 준비**: 대상 프로그램이 처리할 수 있는 작은 입력과 경계 조건을 나타내는 입력을 준비한다.
2. **입력 선택과 변형**: 기존 입력의 바이트·길이·구조 등을 바꾸어 다음 입력을 만든다.
3. **대상 실행**: 파일, 표준 입력, 함수 인자 등 대상에 맞는 방식으로 전달한다.
4. **결과 관찰**: 커버리지, 비정상 종료, 실행 시간, 검사 조건의 위반 여부를 확인한다.
5. **입력 보존과 반복**: 탐색에 도움이 되는 입력은 코퍼스에 추가하고, 실패를 일으킨 입력은 분석할 수 있도록 기록한다.

이 흐름은 모든 퍼저가 동일하게 구현하는 고정 절차는 아니다.  
예를 들어 커버리지를 수집하지 않는 도구는 응답이나 외부에서 관찰한 실패를 중심으로 검사한다.  
커버리지에 따라 입력을 보존하는 기본 원리는 [libFuzzer의 Corpus 설명](https://llvm.org/docs/LibFuzzer.html#corpus)에서도 확인할 수 있다.

#### 구성 요소와 용어

| 용어                  | 의미                                                                           |
| --------------------- | ------------------------------------------------------------------------------ |
| Seed(시드)            | 탐색의 출발점으로 사용하는 입력                                                |
| Corpus(코퍼스)        | 테스트에 사용하는 입력의 모음. 탐색 중 유용한 입력이 추가될 수 있다.           |
| Mutator(변이기)       | 기존 입력의 일부를 바꾸어 새로운 입력을 만드는 구성 요소                       |
| Dictionary(사전)      | 입력 형식에서 의미 있는 키워드나 토큰의 모음                                   |
| Harness(하네스)       | 퍼저의 입력을 검사 대상에 전달하고 필요한 초기화·정리를 수행하는 연결 코드     |
| Fuzz target           | 실제로 검사하는 진입점 또는 함수. 문맥에 따라 대상 프로그램을 가리키기도 한다. |
| Instrumentation(계측) | 실행 위치나 동작을 관찰할 수 있도록 코드를 추가하거나 실행을 추적하는 작업     |
| Coverage(커버리지)    | 실행한 코드의 범위를 나타내는 정보                                             |
| Oracle(오라클)        | 실행 결과를 정상 또는 실패로 판정하는 기준                                     |

하네스와 퍼징 대상 함수는 하나의 코드에 함께 구현되기도 한다.  
문서마다 `fuzzer`라는 말을 엔진, 대상 함수, 실행 파일 등 여러 의미로 사용하므로 문맥을 구분해야 한다.  
[Fuzzing glossary](https://github.com/google/fuzzing/blob/master/docs/glossary.md)

#### 커버리지 종류
**블록 커버리지**는 실행한 기본 블록을, **엣지 커버리지**는 블록 사이의 이동을 관찰한다.  
기본 블록은 중간 분기 없이 순서대로 실행되는 명령어 묶음이다.  
블록이나 엣지를 많이 실행했더라도 가능한 모든 실행 순서와 데이터 상태를 검사한 것은 아니다.

### 종류

퍼징의 종류를 정리할 때는 **내부 정보를 얼마나 사용하는지**, **입력을 어떻게 만드는지**, **대상을 어떻게 실행하는지**를 나누어 보아야 한다.  
하나의 퍼저에 여러 특성이 동시에 적용될 수 있다.

![내부 정보 활용, 입력 생성 방식, 실행 방식의 세 축으로 퍼징을 구분하고 서로 조합할 수 있음을 보여 주는 도식](/assets/images/fuzzing-fuzzer/02-classification-axes.svg)

#### 내부 정보 활용에 따른 분류

| 분류      | 활용하는 정보                           | 특징과 한계                                                               |
| --------- | --------------------------------------- | ------------------------------------------------------------------------- |
| Black-box | 입력·출력과 외부에서 관찰한 동작        | 내부 계측 없이 적용할 수 있지만 어떤 코드까지 실행했는지 파악하기 어렵다. |
| Grey-box  | 커버리지 등 일부 내부 실행 정보         | 비교적 가벼운 피드백으로 입력 탐색을 유도한다.                            |
| White-box | 프로그램의 의미와 실행 조건에 대한 분석 | 기호 실행·제약식 풀이 등을 이용할 수 있지만 분석 비용이 커질 수 있다.     |

**기호 실행(Symbolic execution)**은 입력을 구체적인 값 대신 기호로 취급하면서 분기 조건을 식으로 추적하는 방법이다.  
그 조건을 만족하는 입력을 계산하여 다른 실행 경로를 탐색할 수 있다.  
퍼징과 기호 실행을 결합하는 접근은 **하이브리드 퍼징(Hybrid fuzzing)**으로 설명하기도 한다.

여기서 기준은 소스 코드의 소유 여부가 아니라, 입력 탐색에 어떤 내부 정보를 활용하는가이다.  
소스 코드 없이도 바이너리 계측으로 커버리지를 얻으면 Grey-box 방식으로 탐색할 수 있다.  
분류의 경계가 항상 명확하지는 않다는 점까지 포함해 [퍼징 분류 연구](https://arxiv.org/html/1812.00140)의 기준을 따른다.

#### 입력 생성 방식에 따른 분류

| 분류             | 입력을 만드는 방법                                   | 준비할 내용                                         |
| ---------------- | ---------------------------------------------------- | --------------------------------------------------- |
| Mutation-based   | 기존 입력을 복사하고 일부를 변형한다.                | 대표성 있는 초기 입력, 필요에 따라 사전과 변이 규칙 |
| Generation-based | 문법·메시지 모델 등 규칙을 바탕으로 입력을 구성한다. | 파일 형식이나 프로토콜에 대한 모델                  |

**구조 인지 퍼징(Structure-aware fuzzing)**은 입력의 문법이나 필드 관계를 고려한다.  
기존 입력을 구조로 해석한 뒤 일부 필드를 바꾸는 방식도 가능하므로, 변이 기반과 생성 기반을 완전히 배타적인 범주로 볼 필요는 없다.

설명용 예로 `{"items":[1,2]}`라는 JSON을 생각할 수 있다.  
바이트 단위로 바꾸면 문법이 깨질 수 있고, 구조를 인식하면 배열을 유지하면서 원소 수나 값을 바꿀 수 있다.  
전자는 잘못된 형식의 처리에, 후자는 문법 검사 이후의 처리에 도움이 될 수 있다.  
어느 한쪽만 검사하면 다른 종류의 입력을 놓칠 수 있다. [Structure-Aware Fuzzing](https://github.com/google/fuzzing/blob/master/docs/structure-aware-fuzzing.md)

#### 실행 방식에 따른 구분

| 방식            | 동작                                                               | 고려할 점                                            |
| --------------- | ------------------------------------------------------------------ | ---------------------------------------------------- |
| 프로세스 기반   | 외부 엔진이 대상 프로세스의 실행과 종료를 관리한다.                | 입력마다 시작·초기화 비용이 발생할 수 있다.          |
| In-process      | 퍼징 엔진과 대상 코드가 같은 프로세스에 있고 대상 함수를 호출한다. | 반복 호출 사이에 상태가 남지 않도록 관리해야 한다.   |
| Persistent mode | 하나의 대상 프로세스를 유지하며 여러 입력을 처리한다.              | 초기화 비용을 줄일 수 있지만 상태 초기화가 필요하다. |

이 구분도 서로 완전히 배타적이지 않다.  
외부 엔진이 관리하는 대상 프로세스 안에서 persistent 반복을 수행할 수도 있다.  
AFL++는 준비된 프로세스를 복제하는 **forkserver**로 프로그램을 새로 로드하는 비용을 줄이며, persistent mode도 제공한다.  
따라서 AFL++는 항상 입력마다 새로 시작하고 libFuzzer만 반복 실행한다는 식의 비교는 정확하지 않다. [AFL++ 상세 문서](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/fuzzing_in_depth.md)

---

#### 검사 목적에 따른 접근

- **차등 퍼징(Differential fuzzing)**: 같은 입력에 대한 여러 구현의 결과를 비교한다.  
동일한 명세와 조건에서 비교해야 하며, 차이가 발견되면 원인을 확인한다.
- **속성 기반 검사(Property-based testing)와의 결합**: 다양한 입력에 대해 항상 성립해야 하는 조건을 검사한다.  
예를 들어 유효한 값의 직렬화·역직렬화가 의미를 보존하는지 확인할 수 있다.
- **상태를 고려한 퍼징(Stateful fuzzing)**: 하나의 입력뿐 아니라 앞선 호출이나 메시지의 순서가 이후 동작에 미치는 영향까지 다룬다.

이들은 Black-box·Grey-box와 경쟁하는 별도 분류가 아니라 검사할 성질과 입력 구성에 관한 접근이다.  
차등 검사는 [Google의 퍼징 개요](https://github.com/google/fuzzing/blob/master/docs/intro-to-fuzzing.md), 상태를 가진 API의 입력 모델은 [구조 인지 퍼징 문서](https://github.com/google/fuzzing/blob/master/docs/structure-aware-fuzzing.md)에서 설명한다.

### 오라클과 Sanitizer

입력을 많이 만드는 것만으로 오류를 발견할 수는 없다.  
잘못된 동작을 알아볼 수 있는 **오라클(Oracle)**이 필요하다.

| 관찰할 신호              | 확인할 수 있는 내용                          | 해석할 때의 주의점                                                       |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------------------------ |
| Crash                    | 프로그램이 비정상적으로 종료됨               | 종료 원인과 실제 영향을 확인해야 한다.                                   |
| Sanitizer 진단           | 특정 종류의 메모리 오류나 정의되지 않은 동작 | 사용한 검사 종류와 계측 범위에 따라 탐지 범위가 달라진다.                |
| Assertion·테스트 실패    | 명시한 불변 조건 또는 기대 성질의 위반       | 검사 조건 자체가 올바른지 확인해야 한다.                                 |
| Timeout·메모리 한도 초과 | 정한 자원 한도 내에서 실행하지 못함          | 무한 반복인지, 큰 입력의 정상 처리인지, 한도가 부적절한지 구분해야 한다. |
| 구현 간 결과 차이        | 같은 입력에 대한 동작 불일치                 | 명세상 허용되는 차이와 구현 오류를 구분해야 한다.                        |

**Sanitizer**는 실행 중 특정 오류를 감지하는 도구이다.  
예를 들어 잘못된 메모리 접근이 즉시 충돌하지 않더라도, 계측을 통해 오류를 보고할 수 있다.

- **AddressSanitizer(ASan)**: 버퍼 범위 밖 접근, 해제 후 사용(Use-after-free) 등의 메모리 오류를 감지한다. [공식 문서](https://clang.llvm.org/docs/AddressSanitizer.html)
- **UndefinedBehaviorSanitizer(UBSan)**: 부호 있는 정수 오버플로 등 여러 종류의 정의되지 않은 동작을 검사한다. [공식 문서](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)

커버리지 계측과 Sanitizer는 목적이 다르다.  
커버리지는 다음에 무엇을 탐색할지 판단하는 데 쓰이고, Sanitizer는 실행 중 무엇이 잘못되었는지 감지하는 데 쓰인다.  
또한 UBSan의 일부 검사는 진단 후 실행을 계속할 수 있으므로, 진단을 퍼징 실패로 인식하는지는 실행 설정과 연동 방식에 달려 있다.

### 하네스의 중요성

전체 애플리케이션을 실행하면 설정 로딩이나 화면 초기화에 많은 시간을 쓸 수 있다.  
파일 파서처럼 검사하려는 기능을 작은 진입점으로 연결하면 반복 실행에 필요한 작업을 줄일 수 있다.

하네스에서는 다음을 확인한다.

1. **대상 도달 여부**: 생성된 입력이 실제 검사할 기능까지 전달되는가?
2. **다양한 입력 처리**: 빈 입력·잘못된 형식도 대상의 입력 처리 경로로 전달되는가?
3. **결정성**: 같은 입력과 조건에서 동작이 일관되는가?
4. **상태 관리**: 반복 실행 사이에 전역 상태·캐시·자원이 의도치 않게 남는가?
5. **검사 조건**: 정상적인 입력 거부와 프로그램 오류를 구분하는가?

예를 들어 파서가 잘못된 형식을 오류 값으로 반환하는 것은 정상 동작일 수 있다.  
모든 입력 거부를 버그로 처리하면 실패 결과의 의미가 흐려진다.  
반대로 하네스가 유효한 입력만 통과시키면 대상이 잘못된 입력을 처리하는 부분을 검사하지 못할 수 있다.  
대상의 크기·결정성·상태·입력 집합에 관한 기준은 [좋은 Fuzz target의 조건](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md)을 참고하였다.

## Fuzzer

### 정의

**퍼저(Fuzzer)**는 퍼징을 수행하는 도구이다.  
입력 생성·변이, 실행 관리, 피드백 수집, 입력 보존 등의 기능을 제공하며, 일부는 특정 역할에 집중한다.

이 글에서는 AFL++·libFuzzer 같은 퍼징 엔진뿐 아니라 boofuzz 같은 프레임워크와 언어에 내장된 퍼징 기능도 함께 살펴본다.  
도구마다 입력 형식, 계측 방법, 검사 대상이 다르므로 이름이나 인지도만으로 선택하기는 어렵다.

---

### 종류

#### [AFL++](https://github.com/AFLplusplus/AFLplusplus)

**AFL++**는 AFL을 바탕으로 계측·변이·실행 방식을 확장한 커버리지 유도 퍼저이다.  
기존 입력을 변형하고, 새로운 실행 정보를 제공한 입력을 보존하며 탐색한다.

소스 코드가 있으면 컴파일 과정에서 계측을 추가할 수 있다.  
소스 코드가 없는 대상에도 QEMU·FRIDA 등의 방식을 이용할 수 있지만, 운영체제·아키텍처·실행 모드에 따른 지원 조건은 확인해야 한다.  
파일을 읽는 프로그램뿐 아니라 하네스로 연결한 라이브러리도 검사할 수 있다. 

선택할 수 있는 실행 방식이 많고 기존 하네스를 활용하기 좋다는 장점이 있다.  
그만큼 대상에 맞는 계측 방식과 상태 관리 방법을 정하는 준비가 필요하다.  
`LLVMFuzzerTestOneInput` 형식의 하네스도 활용할 수 있으므로,  
하네스의 함수 이름만으로 실행 엔진을 판단할 수는 없다. 

> LLVMFuzzerTestOneInput: 후술할 libFuzzer의 표준 진입점 함수  
> 즉, `LLVMFuzzerTestOneInput`이라는 함수 이름이 있다고 해서 무조건 libFuzzer로 실행되는 것은 아니다.

---

#### [Jackalope](https://github.com/googleprojectzero/Jackalope)

**Jackalope**는 바이너리 대상을 검사할 수 있는 커버리지 유도 퍼저이다.  
기본 계측 구성 요소로 **TinyInst**를 사용하며, 입력 전달·변이·계측 구성 요소를 교체할 수 있도록 설계되어 있다.

파일이나 공유 메모리로 입력을 전달할 수 있고, 여러 작업자 사이에서 유용한 입력과 커버리지 정보를 공유할 수 있다.  
README에는 Windows·macOS·Linux·Android가 지원 대상으로 명시되어 있다.  
Linux에서는 소스 코드가 필요한 SanitizerCoverage 방식도 별도로 안내한다.  

바이너리의 실행을 관찰하거나 입력 전달 방식을 대상에 맞게 바꾸어야 할 때 검토할 수 있다.  
다만 바이너리를 실행할 수 있다는 것만으로 원하는 기능에 입력이 자동 연결되지는 않는다.  
호출할 기능과 입력 전달 방식을 이해하고, 해당 환경에서 계측이 안정적으로 동작하는지 확인해야 한다.

README의 `black-box binaries`라는 표현은 소스가 없는 대상도 다룬다는 맥락이다.  
앞서 설명한 분류 기준을 적용하면, 커버리지 피드백을 이용하는 기본 탐색 방식은 Grey-box로 이해할 수 있다.  

---

#### [libFuzzer](https://llvm.org/docs/LibFuzzer.html)

**libFuzzer**는 LLVM의 in-process 커버리지 유도 퍼징 엔진이다.  
대상 라이브러리와 엔진을 연결하고, 입력을 받는 함수를 같은 프로세스에서 반복 호출한다.  
커버리지 정보는 LLVM의 SanitizerCoverage 계측으로 얻는다.

작은 라이브러리 함수나 파서를 테스트에 연결하기 좋다.  
반복 호출 사이에 상태가 남거나 대상이 프로세스를 종료하면 정상적인 탐색을 방해할 수 있어 하네스 설계가 중요하다.

공식 문서의 유지보수 안내에 따르면 원저자들은 적극적인 개발을 중단하고 다른 엔진으로 작업을 옮겼다.  
중요한 버그 수정은 지원하지만 큰 새 기능을 기대하기는 어렵다고 명시되어 있다.  
기존 활용도와 현재 개발 상태를 구분해서 판단해야 한다.  

---

#### [Honggfuzz](https://github.com/google/honggfuzz)

**Honggfuzz**는 실행 피드백을 이용하는 범용 퍼저이다.  
소프트웨어 계측과 Intel PT 같은 하드웨어 기반 실행 추적을 지원하고, 병렬 실행 및 persistent 방식도 제공한다.

외부 프로그램과 함수 단위 검사 등 여러 실행 형태를 검토할 수 있다는 장점이 있다.  
하드웨어 피드백을 사용하려면 CPU·운영체제·접근 권한 등 해당 모드의 조건이 맞아야 한다.  

---

#### [boofuzz](https://boofuzz.readthedocs.io/en/stable/)

**boofuzz**는 Python으로 메시지 구조와 통신 흐름을 정의하는 프로토콜 퍼징 프레임워크이다.  
메시지의 필드와 전송 순서를 모델링하고, 값을 바꾸어 전달하며 대상의 실패를 관찰한다.  

요청 사이의 선행 관계를 표현할 수 있어 여러 메시지가 순서대로 필요한 대상을 다루는 데 도움이 된다.  
커버리지에 따라 코퍼스를 발전시키는 엔진과는 기본 사용 방식이 다르며, 메시지 모델·응답 확인·장애 감지·대상 재설정에 대한 준비가 필요하다.  
프로토콜 모델을 만드는 것과 대상의 모든 상태를 자동으로 추론하는 것은 구분해야 한다.  

---

#### [syzkaller](https://github.com/google/syzkaller)

**syzkaller**는 운영체제 커널을 대상으로 하는 커버리지 유도 퍼저이다.  
시스템 호출에 대한 설명을 바탕으로 호출 시퀀스를 생성·변형하고, 실행 결과와 커버리지를 관찰한다.

일반적인 파일 파서와 검사 단위가 다르며, 가상 머신 관리와 커널의 실행·관찰 환경이 중요하다.  
공식 구조 문서는 관리 프로세스가 VM을 시작·감시하고, VM 안의 실행기가 시스템 호출 시퀀스를 실행하는 구성을 설명한다.  
커널 검사에 필요한 기능을 제공하는 만큼 환경 준비와 결과 분석의 부담도 있다.  

---

#### [Go 내장 퍼징](https://go.dev/doc/security/fuzz/)

**Go의 내장 퍼징**은 표준 테스트 도구 모음에 통합된 커버리지 유도 퍼징 기능이다.  
`testing` 패키지의 퍼징 테스트에서 입력과 검사 조건을 정의하며, 실패 입력을 일반 테스트에서 다시 확인할 수 있다.

Go 함수의 성질을 검사할 때 기존 테스트 흐름과 연결하기 좋다.  
메모리 안전성을 지원하는 언어에서도 panic, 잘못된 결과, 경계 조건 처리 오류가 발생할 수 있으므로 퍼징이 유용하다.  
외부의 임의 바이너리를 검사하는 도구와 적용 범위는 다르다.

#### 소스 코드 유무와 계측 방식

![소스와 하네스를 컴파일하면서 계측하는 경로와 기존 바이너리를 실행 중 계측하는 경로가 모두 커버리지 피드백으로 이어지는 구조](/assets/images/fuzzing-fuzzer/03-instrumentation-paths.svg)

왼쪽은 소스 코드를 빌드하면서 관찰 지점을 넣는 방식이다.  
오른쪽은 기존 바이너리가 실행되는 동안 동작을 추적하는 방식이다.  
AFL++의 바이너리 지원과 Jackalope의 TinyInst 구성은 오른쪽 방식도 가능함을 보여 준다.  

두 방식 모두 계측 범위 밖의 코드를 모두 자동으로 관찰하는 것은 아니다.  
동적 라이브러리까지 검사할 것인지, 원하는 기능까지 실행되는지에 따라 실제 피드백의 의미가 달라진다.

#### 도구를 고를 때 확인할 순서

다음은 위 기능 비교를 바탕으로 정리한 판단 기준이다.

1. **검사 단위**: 파일 파서, 라이브러리 함수, 프로토콜, 커널 중 무엇을 검사하는가?
2. **빌드 가능 여부**: 소스 코드를 수정·빌드할 수 있는가, 바이너리만 사용할 수 있는가?
3. **입력 진입점**: 파일·함수 인자·메시지 중 어떤 형태로 입력을 전달하는가?
4. **관찰 가능 범위**: 커버리지·Sanitizer·외부 모니터 중 무엇을 사용할 수 있는가?
5. **반복 실행 조건**: 상태를 초기화할 수 있으며 같은 입력의 결과가 일관되는가?

예를 들어 직접 개발한 Go 함수에는 내장 퍼징을,  
빌드 가능한 C/C++ 라이브러리에는 libFuzzer·AFL++·Honggfuzz를 검토할 수 있다.  
바이너리 계측이 필요하면 Jackalope나 AFL++의 해당 모드를, 메시지 순서 모델이 중요하면 boofuzz를 검토할 수 있다.

### Fuzzing의 장단점

#### 장점

- **입력 탐색 자동화**: 사람이 모두 작성하기 어려운 값과 조합을 반복적으로 검사할 수 있다.
- **경계 조건 검사**: 빈 입력, 길이 변화, 예상하지 못한 값의 조합을 다루는 데 도움이 된다.
- **실행 증거 확보**: 실패 입력과 진단을 보존하면 수정과 회귀 테스트에 활용할 수 있다.
- **개발 과정과 연결**: 기존 테스트에 입력 집합과 검사 조건을 추가하여 지속적으로 품질을 확인할 수 있다.

효과는 입력을 만드는 엔진뿐 아니라 검사 대상과 하네스의 품질에도 좌우된다.  
발견된 실패 입력을 테스트에 보존하는 흐름은 [좋은 Fuzz target의 조건](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md)에서도 다룬다.

---

#### 단점 및 한계

| 한계                                 | 이유                                                                    |
| ------------------------------------ | ----------------------------------------------------------------------- |
| 오류가 없다는 보장은 어렵다.         | 유한한 시간 동안 일부 입력과 상태만 실행한다.                           |
| 깊은 처리까지 도달하지 못할 수 있다. | 입력 형식이 자주 깨지거나 초기 검사에서 거부될 수 있다.                 |
| 논리 오류를 놓칠 수 있다.            | 잘못된 결과를 내더라도 검사할 성질이 없으면 정상으로 보일 수 있다.      |
| 실행 자원이 필요하다.                | 반복 실행·계측·Sanitizer·환경 재설정에 시간과 메모리를 사용한다.        |
| 실패 원인 분석이 필요하다.           | 대상 코드, 하네스, 환경 설정 중 어디서 문제가 발생했는지 구분해야 한다. |

커버리지 증가도 곧바로 보안성 향상의 수치가 되지는 않는다.  
같은 코드 경로에서 값에 따라 다른 오류가 발생할 수 있고, 실행한 코드에 오류 판정 기준이 충분하지 않을 수도 있다.  
입력 형식 때문에 탐색이 제한되는 문제는 [구조 인지 퍼징 문서](https://github.com/google/fuzzing/blob/master/docs/structure-aware-fuzzing.md)에서 설명한다.

---

### 결과를 읽을 때 확인할 지표

| 지표                   | 의미                               | 함께 확인할 내용                              |
| ---------------------- | ---------------------------------- | --------------------------------------------- |
| 실행 횟수·초당 실행 수 | 얼마나 많은 입력을 처리했는가      | 같은 초기 검사만 반복하는 것은 아닌가?        |
| 커버리지               | 관찰한 코드 범위가 얼마나 늘었는가 | 같은 빌드·측정 방식·계측 범위인가?            |
| 코퍼스 크기            | 보존한 입력이 얼마나 되는가        | 중복이 많지 않고 서로 다른 동작을 대표하는가? |
| 실패 입력 수           | 실패로 판정한 입력이 얼마나 되는가 | 같은 원인의 중복 입력인가?                    |
| 실행 안정성            | 같은 조건에서 결과가 일관되는가    | 상태 누적이나 환경 변화가 영향을 주는가?      |

도구마다 내부 커버리지 표현과 계측 범위가 다를 수 있어 화면에 표시된 숫자만 직접 비교하기는 어렵다.  
같은 대상·초기 입력·자원 조건을 맞추고, 공통 측정 기준과 여러 번의 시행을 이용해야 비교의 의미가 생긴다.  
FuzzBench도 여러 벤치마크와 반복 실험, 통계 분석을 통해 결과를 평가한다. [FuzzBench](https://google.github.io/fuzzbench/)

---

### 실패 입력에서 회귀 테스트까지

퍼징으로 저장된 실패 입력은 원인 분석의 출발점이다.  
크래시 파일 여러 개가 같은 버그에서 나올 수도 있으며,  
비정상 종료가 발견되었다고 곧바로 악용 가능한 취약점으로 확정되는 것은 아니다.

입력을 정리할 때는 두 가지 최소화를 구분한다.

- **코퍼스 최소화**: 관찰한 커버리지 등 필요한 특성을 유지하면서 입력 집합의 중복을 줄인다.
- **실패 입력 최소화**: 같은 실패를 유지하면서 한 입력의 불필요한 부분을 줄인다.

원인을 수정한 뒤에는 해당 입력을 **회귀 테스트(Regression test)**에 남긴다.  
> **회귀 테스트**: 코드 변경 뒤에 이전 문제가 다시 생기거나 기존 기능이 깨지는지 확인하는 테스트  

이때 실패 입력과 함께 대상 버전·하네스·빌드 옵션·진단 조건을 기록해야 결과를 해석할 수 있다.  
입력 집합 관리와 테스트 통합은 [libFuzzer의 Corpus 설명](https://llvm.org/docs/LibFuzzer.html#corpus) 및 [좋은 Fuzz target의 조건](https://github.com/google/fuzzing/blob/master/docs/good-fuzz-target.md)을 참고하였다.

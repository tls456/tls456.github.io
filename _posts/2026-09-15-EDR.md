## 사전 조사

### EDR
#### 정의
**EDR(Endpoint Detection and Response, 엔드포인트 탐지 및 대응)**: 엔드포인트에서 일어나는 활동을 지속적으로 수집·분석하여 의심스러운 행위를 탐지하고, 조사하고, 대응하는 보안 솔루션

**Endpoint(엔드포인트)**: 네트워크의 끝단에서 실제 사용자가 사용하는 장치나 서버  

---

#### 등장 배경
기존 전통적인 엔드포인트 보안은 **안티바이러스(AV, 백신)** 이 중심

**백신의 목적**: 엔드포인트에 들어온 악성코드를 찾아 차단

**백신의 한계**: 공격 방식의 복잡화로 단순 악성 파일 탐색만으로 부족해지기 시작

**예시 시나리오**: 악성 실행 파일을 설치하지 않고 PowerShell로 공격

**또 다른 한계점**: 침해 발생 이후 조사의 어려움

**침해 사고 조사에서 필요한 정보**
1. 최초에 어떤 프로세스가 실행되었는가?
2. 그 프로세스는 누가 실행했는가?
3. 이후 어떤 자식 프로세스가 실행되었는가?
4. 어떤 파일이 생성되거나 변경되었는가?
5. 외부 시스템과 통신했는가?
6. 다른 시스템으로 공격이 확산되었는가? 

이러한 정보들을 악성 파일 존재만으로 파악할 수 없다. 

즉, 엔드포인트에서 발생한 행위에 대한 지속적인 기록이 필요하다.  

---

#### 목적
1. 엔드포인트에서 발생하는 다양한 행위를 지속적으로 관찰하여 위협 탐지
2. 수집된 기록을 바탕으로 공격 조사 및 대응

Endpoint Detection and Response: 엔드포인트 탐지 및 대응  

---

#### 동작 흐름과 원리
**전체 동작 흐름**  
```
① 데이터 수집 (Sensor/Agent)
        ↓
② 데이터 전송 및 저장 (중앙 서버/클라우드)
        ↓
③ 분석 및 탐지 (시그니처/행위/ML 기반)
        ↓
④ 알림 및 시각화 (SOC/관리자에게 표시)
        ↓
⑤ 대응 (격리, 프로세스 종료, 롤백 등)
```

---

##### **1. 데이터 수집 단계**
엔드포인트에 설치된 에이전트가 시스템 이벤트를 지속적으로 수집/모니터링

수집 대상 이벤트 예시:
- 프로세스 생성/종료 (부모-자식 프로세스 관계 포함)
- 파일 생성/수정/삭제
- 레지스트리 변경 (Windows)
- 네트워크 연결 (소켓 오픈, DNS 쿼리 등)
- 로그인/로그아웃, 권한 상승
- DLL 로드, 메모리 인젝션 시도
- 명령줄 인자(command line arguments)

---

##### **2. 데이터 전송 및 저장**
수집된 데이터는 로컬에서 1차로 필터링된 후, 클라우드/온프레미스 관리 서버로 전송 = 중앙 집중식 저장  

---

##### **3. 분석 및 탐지**

여러 탐지 레이어 동시 작동  

| 탐지 방식              | 설명                                                                                    |
| ---------------------- | --------------------------------------------------------------------------------------- |
| 시그니처 기반          | 알려진 악성코드의 특징/패턴 등을 기반으로 탐지                                          |
| IOC 기반               | 악성 해시·IP·Domain 등 알려진 침해 지표와 대조                                          |
| 행위 기반 (Behavioral) | 정상 패턴을 벗어난 행위 시퀀스 탐지 (예: Word가 PowerShell을 실행하고 외부 서버로 연결) |
| 규칙/룰 기반           | 로그·이벤트 또는 파일/메모리 등의 특정 패턴을 정의한 탐지 규칙 활용(Sigma, YARA 등)     |
| 머신러닝/AI 기반       | 통계적 이상치 탐지, 사전 학습된 모델로 알려지지 않은 위협 예측                          |
| 위협 인텔리전스 연동   | 외부 Threat Intelligence를 이용해 IOC 및 공격 정보를 보강                               |
| MITRE ATT&CK 매핑      | 탐지된 행위를 공격 기법(TTP) 단위로 분류                                                |

---

##### **4. 알림 및 시각화**

탐지된 이벤트의 심각도에 따라 알림(Alert)이 발생  
SOC(Security Operations Center) 분석가가 대시보드에서 프로세스 트리, 타임라인, 네트워크 흐름등을 시각적으로 확인  
단순 탐지를 넘어 어떤 일이 어떤 순서로 발생했는지 확인  

---

##### **5. 대응 (Response)**

탐지 후 자동/수동으로 대응 조치

**예시:** 
- 엔드포인트 네트워크 격리(isolation)
- 악성 프로세스 강제 종료
- 파일 삭제/격리(quarantine)
- 레지스트리 롤백
- 원격으로 스크립트 실행(추가 조사/치료)  

---  

### Elastic Stack
**Elastic Stack**: 데이터를 수집·저장·검색·분석·시각화하는 오픈소스 기반 도구 모음

#### 핵심 구성 요소

1. **Elasticsearch**: 수집된 데이터를 저장하고 검색·분석하는 엔진  
EDR 관점에서는 프로세스 실행, 파일 활동, 네트워크 활동 등의 데이터가 저장되는 곳
2. **Kibana**: Elasticsearch의 데이터를 사람이 확인하고 분석할 수 있게 해주는 웹 인터페이스
3. **Fleet**: 여러 Elastic Agent와 그 설정을 중앙에서 관리   
즉, "어떤 Agent가 연결되어 있는가?", "이 Agent에는 어떤 정책을 적용할 것인가?" 등을 관리 

---  

### Elastic Agent
**Elastic Agent**: Endpoint에 설치되는 범용 Agent

**역할**: 데이터를 수집하고 중앙의 Elastic 환경과 통신

---

### Elastic Defend
**Elastic Defend**: Elastic Agent를 통해 Endpoint에 적용되는 보안 Integration

**역할**: Endpoint의 보안 이벤트를 수집하고 악성코드 및 의심 행위 등을 탐지·예방

즉, Elastic Agent = Endpoint에 설치되는 실행 주체/기반  
Elastic Defend = Agent를 통해 동작하는 EDR/보안 기능  

---

### Fleet Server와 Agent Policy
**Fleet Server**: Endpoint의 Elastic Agent와 Fleet 사이에서 관리 통신하는 서버

**Agent Policy**: Agent에게 적용할 설정 묶음  

예시: "Elastic Defend를 Agent Policy에 추가한다"   
= 이 정책을 적용받는 Agent에서 Endpoint 보안 기능을 사용하도록 설정한다.  

---  

### Integration
**Integration**: 특정 데이터나 기능을 Elastic Agent에 연결하기 위한 패키지  

예시:
```
Elastic Agent
 ├─ System Integration
 │    → OS 관련 데이터
 │
 └─ Elastic Defend Integration
      → Endpoint 보안 데이터
```

---

### Event, Detection, Alert
**Event**: Endpoint에서 발생한 활동에 대한 기록  

예시:
- powershell.exe 실행
- 파일 생성
- 네트워크 연결
- 프로세스 생성

**Detection**: 데이터를 분석하여 위협 가능성이 있는 행위를 찾아내는 것  

**Alert**: 탐지 결과 중 보안 담당자가 확인·조사할 수 있도록 만들어진 경고  

---  

### Telemetry
Telemetry: Endpoint에서 수집하여 보내는 관측 데이터 전반  

예시: 
- 프로세스 생성 정보
- 파일 활동
- 네트워크 연결
- 사용자 활동

---

### Detect VS Prevent
**Detect(탐지)**: 위협 행위 → 탐지 → 기록/Alert  
**Prevent(예방)**: 위협 행위 → 탐지 → 차단

---  

### Process Tree와 Parent/Child Process  

운영체제에서 프로세스가 다른 프로세스를 실행하면 부모-자식 관계가 형성  

**Parent Process(부모 프로세스)**: 새로운 프로세스를 생성(fork/spawn)한 쪽  
**Child Process(자식 프로세스)**: 그 결과로 생성된 새 프로세스  

**Process Tree(프로세스 트리)**: 부모-자식 관계를 트리 구조로 표현한 것  

예시:
```
explorer.exe
    │
    └─ cmd.exe
         │
         └─ powershell.exe
              │
              └─ another.exe
```

EDR은 단순히 "powershell.exe가 실행됐다"만 보는 것이 아니라   
"누가 PowerShell을 실행했는가"까지 확인하여 분석  

---  

### EICAR  
**EICAR Anti-Malware Test File**: 실제 악성코드를 사용할 필요 없이 안티멀웨어 제품의 탐지 동작을 시험하기 위해 만들어진 표준 테스트 파일  

---

```
┌──────── Windows Endpoint ────────┐

    프로세스 / 파일 / 네트워크 활동

```

## 실제 구현
### 구현 구조
```
Windows Host
│
└─ VMware Workstation
    │
    ├─ Ubuntu Server VM
    │   └─ Elastic 환경
    │      ├─ Elasticsearch
    │      │   └─ 이벤트 저장·검색
    │      ├─ Kibana / Elastic Security
    │      │   └─ 조회·탐지·분석
    │      └─ Fleet Server
    │          └─ Agent 관리 통신
    │
    └─ Windows VM
        └─ Endpoint
           └─ Elastic Agent
               └─ Elastic Defend Integration
                   └─ Endpoint 보안 이벤트 수집
```
### 실습 환경

| 구분           | 환경                          | 용도                                      |
| -------------- | ----------------------------- | ----------------------------------------- |
| Host           | Windows                       | 가상 머신 실행                            |
| Virtualization | VMware Workstation Pro 26H1u1 | 실습용 가상 머신 구성                     |
| EDR Server     | Ubuntu Server 26.04.1 LTS     | Elasticsearch, Kibana, Fleet Server 실행  |
| Endpoint       | Windows                       | Elastic Agent 설치 및 Elastic Defend 적용 |

실습을 진행하는 노트북의 메모리가 16GB이므로   
Elastic 환경을 실행하는 Ubuntu VM에는 6GB,  
Endpoint로 사용하는 Windows VM에는 4GB 메모리 할당

실제 Host PC를 Endpoint로 사용하지 않고 별도의 Windows VM 구성을 통해  
EDR 실습 환경을 실제 사용 환경과 분리하고,    
문제가 발생할 경우
VM의 스냅샷을 이용하여 이전 상태로 쉽게 복구할 수 있도록 함

[VMware Workstation Pro 다운로드](https://support.broadcom.com/group/ecx/productdownloads?subfamily=VMware%20Workstation%20Pro&freeDownloads=true)

[Ubuntu Server ISO 다운로드](https://ubuntu.com/download/server)

### 환경 구축
#### 1. Elastic EDR 환경 구축

먼저 Ubuntu Server VM에 Elastic Stack을 구축하였다.

이번 실습에서는 Elastic Security Labs에서 공개한 **Elastic Container Project**를 이용하여 Docker 기반으로 Elasticsearch, Kibana, Fleet Server를 구성하였다.

Elastic Container Project는 보안 연구 및 테스트를 목적으로 Elastic Stack 환경을 빠르게 구성할 수 있도록 Docker Compose 기반으로 만들어진 프로젝트이다.

```bash
git clone https://github.com/peasead/elastic-container.git
cd elastic-container
```

프로젝트를 내려받은 뒤 `.env` 파일의 설정값을 실습 환경에 맞게 수정하고 Elastic 환경을 실행하였다.

```bash
./elastic-container.sh start
```

실행이 완료되면 주요 구성은 다음과 같다.

```text
Ubuntu Server
│
├─ Elasticsearch
│   └─ Endpoint에서 수집된 데이터 저장 및 검색
│
├─ Kibana
│   └─ 데이터 조회, Detection Rule, Alert 분석
│
└─ Fleet Server
    └─ Endpoint의 Elastic Agent 관리
```

#### 3. Elastic Defend 추가

Endpoint에서 보안 이벤트를 수집하기 위해 Agent Policy에 **Elastic Defend Integration**을 추가하였다.

Kibana에서 다음과 같이 이동한다.

```text
Fleet
→ Agent policies
→ Endpoint Policy
→ Integrations
→ Elastic Defend
```

Elastic Defend는 Elastic Agent를 통해 Endpoint의 프로세스, 파일, Registry 등의 보안 관련 활동을 수집하고 탐지 기능을 제공한다.

이번 실습에서 사용한 Endpoint Policy에는 다음 두 Integration이 적용되어 있다.

```text
Endpoint Policy
├─ System
└─ Elastic Defend
```

#### 4. Windows Endpoint 구성

실제 Host PC와 EDR 실습 환경을 분리하기 위해 별도의 Windows VM을 Endpoint로 구성하였다.

Windows VM과 Ubuntu Server VM은 VMware NAT 네트워크를 통해 통신하도록 구성하였다.

구조는 다음과 같다.

```text
Windows Host
│
└─ VMware NAT Network
    │
    ├─ Ubuntu Server
    │   └─ Elastic Stack / Fleet Server
    │
    └─ Windows VM
        └─ Elastic Agent / Elastic Defend
```

Agent 설치 전 Windows Endpoint에서 Fleet Server와 통신할 수 있는지 확인하였다.

PowerShell에서 다음 명령을 사용하였다.

```powershell
Test-NetConnection Elastic-Server-IP -Port 8220
```

결과에서 다음 값이 확인되면 Fleet Server와 TCP 연결이 가능한 상태이다.

```text
TcpTestSucceeded : True
```

#### 5. Elastic Agent 설치 및 Fleet 등록

Kibana의 Fleet에서 `Endpoint Policy`를 선택하고 Windows용 Elastic Agent를 설치하였다.

Windows VM은 x86-64 환경이므로 Windows x86_64용 Elastic Agent를 사용하였다.

Agent 설치 후 Fleet Server에 Enrollment를 수행하였다.

이번 실습 환경의 Fleet Server는 자체 서명 인증서를 사용하고 있기 때문에 인증서 검증 과정에서 신뢰할 수 없는 인증서라는 오류가 발생할 수 있다.

실습 환경에서는 자체 서명 인증서를 사용하는 것을 확인한 뒤 `--insecure` 옵션을 이용하여 Enrollment를 진행하였다.

```powershell
elastic-agent.exe enroll `
  --url=https:// Elastic-Server-IP :8220 `
  --enrollment-token= ENROLLMENT-TOKEN `
  --insecure
```

등록 완료 후 Elastic Agent의 상태를 확인하였다.

```powershell
& "C:\Program Files\Elastic\Agent\elastic-agent.exe" status
```

정상적으로 연결되면 Fleet과 Elastic Agent가 `HEALTHY` 상태로 표시된다.

#### 8. Detection Rule 생성

수집된 Process Event를 실제 Alert로 변환하는 과정을 확인하기 위해 테스트용 Detection Rule을 생성하였다.

Kibana에서 다음과 같이 이동하였다.

```text
Security
→ Rules
→ Detection rules
→ Create new rule
→ Custom query
```

Custom Query에는 다음 KQL을 사용하였다.

```text
process.name : "calc.exe" and event.action : "start"
```

Rule의 기본 정보는 다음과 같이 설정하였다.

```text
Name
Lab - Calculator Process Execution

Description
Detects calc.exe process execution for EDR lab testing.

Severity
Low

Risk score
21
```

Rule은 5분마다 실행되도록 설정하고 추가 Look-back Time을 1분으로 설정하였다.

```text
Runs every              : 5 minutes
Additional look-back    : 1 minute
```

이번 Rule의 목적은 프로세스 차단이 아니라 **Event → Detection → Alert의 흐름을 확인하는 것**이므로 별도의 Response Action은 설정하지 않았다.

### Alert 분석

#### 10. Visual Event Analyzer를 이용한 Process Tree 분석

생성된 Alert를 **Visual Event Analyzer**로 분석하였다.

Visual Event Analyzer는 Process Event의 부모-자식 관계를 기반으로 해당 프로세스가 어떤 실행 흐름을 통해 생성되었는지 시각적으로 확인할 수 있게 해준다.

![image12](/assets/images/EDR/image12.png)  

이번 실습에서는 다음과 같은 Process Tree를 확인할 수 있었다.

```text
winlogon.exe
      ↓
userinit.exe
      ↓
explorer.exe
      ↓
wt.exe
      ↓
Windows Terminal
      ↓
powershell.exe
      ↓
calc.exe
```

즉 단순히

```text
calc.exe가 실행됨
```

이라는 사실만 확인하는 것이 아니라,

```text
어떤 사용자 환경에서
→ 어떤 터미널이 실행되고
→ 어떤 PowerShell 프로세스를 거쳐
→ calc.exe가 실행되었는가
```

라는 실행 문맥을 확인할 수 있다.

---

#### 11. Parent/Child Process 관계 분석

Analyzer에서 `powershell.exe`와 `calc.exe`를 각각 선택하여 상세 정보를 확인하였다.

PowerShell에서는 다음 정보를 확인할 수 있었다.

![image13](/assets/images/EDR/image13.png)  

```text
Process : powershell.exe
PID     : 8452
```

그리고 `calc.exe`에서는 다음과 같이 나타났다.

![image14](/assets/images/EDR/image14.png)  

```text
Process    : calc.exe
PID        : 25956
Parent PID : 8452
```

따라서 다음 관계를 직접 확인할 수 있었다.

```text
powershell.exe
PID = 8452
      │
      └── calc.exe
          PID = 25956
          Parent PID = 8452
```

즉 Process Tree의 시각적인 연결뿐만 아니라 실제 Process Event의 PID 정보에서도 `powershell.exe`가 `calc.exe`의 부모 프로세스임을 확인할 수 있었다.

---

#### 12. Process 관련 Event 분석

`calc.exe`에는 Process Event 외에도 실행 과정에서 발생한 여러 Registry Event가 연결되어 있었다.

Analyzer에서 확인한 결과 총 4개의 Registry 관련 Event가 존재하였다.

![image16](/assets/images/EDR/image16.png) 

```text
calc.exe
│
├─ Registry Access
├─ Registry Change
├─ Registry Change
└─ Registry Change
```

Registry Access Event의 상세 정보를 확인한 결과 다음과 같은 정보를 확인할 수 있었다.

![image15](/assets/images/EDR/image15.png)  

```text
process.name
calc.exe

process.executable
C:\Windows\System32\calc.exe

registry.key
SOFTWARE\VMware, Inc.\VMwareHostOpen\Capabilities\UrlAssociations

registry.value
ms-calculator
```

즉 EDR은 프로세스가 실행되었다는 사실만 저장하는 것이 아니라 해당 프로세스와 연결된 Registry 등의 활동도 함께 기록하고 분석에 활용할 수 있다.

다만 Registry 접근이나 변경 Event가 존재한다는 사실 자체가 악성 행위를 의미하지는 않는다. 정상 프로그램에서도 Registry 접근은 일반적으로 발생하므로 실제 보안 분석에서는 프로세스 실행 문맥과 다른 Event들을 함께 분석해야 한다.

---

#### 13. Process Tree가 나타나지 않았던 문제 분석

Visual Event Analyzer를 처음 확인했을 때에는 전체 Process Tree가 나타나지 않고 `calc.exe` 하나만 표시되었다.

`calc.exe` Event 자체에는 다음과 같이 부모 프로세스 정보가 존재하였다.

```text
process.parent.name      = powershell.exe
process.parent.entity_id = <Parent Entity ID>
```

하지만 해당 `process.parent.entity_id`를 자신의 `process.entity_id`로 가진 부모 Process Event를 검색했을 때 결과가 존재하지 않았다.

당시 Windows VM을 재부팅한 직후 Elastic Agent의 Fleet 연결 상태가 아직 `STARTING`이었던 상태에서 기존 PowerShell을 사용하고 있었다.

Elastic Agent가 정상적으로 동작하는 상태에서 새로운 PowerShell을 실행한 뒤 다시 `calc.exe`를 실행하자 이번에는 전체 Process Tree가 정상적으로 구성되었다.

이를 통해 **자식 Process Event에 부모 프로세스의 정보가 기록되어 있는 것과 부모 Process Event 자체가 EDR에 수집되어 있는 것은 별개의 문제**라는 것을 확인할 수 있었다.

또한 Process Tree를 구성하려면 단순히 Process Name이나 PID만 확인하는 것이 아니라 `process.entity_id`와 `process.parent.entity_id`처럼 각각의 프로세스 실행 인스턴스를 식별할 수 있는 정보가 중요하다는 점을 확인하였다.

## 느낀 점
보안 솔루션을 구동하고 결과를 분석하며 실제로 서비스를 관제하는 실무자가 된 것 같아 흥미로웠다.    

또한 제공하는 기능이 많은 만큼, 최소한의 시스템 리소스를 사용하여 필요한 보안 기능을 제공하기 위해 많은 노력이 필요할 것이라는 생각이 들었다.  

실제로 이번 실습을 RAM 16GB의 노트북으로 진행하였는데, VM 두 개를 실행하다 보니 컴퓨터 팬 소리를 듣고 하늘로 날아가는 줄 알았다.  

Endpoint를 위한 VM은 실제 보안 솔루션에 필요한 리소스가 아니지만 보안 솔루션이 동작중인 상황에서 회사의 모든 인원이 업무를 수행해야 하다 보니 최대한 효율적으로 리소스를 사용하는 것이 중요하다는 것을 느낀 것이다.  

그래서 다음으로는 EDR을 비롯한 보안 솔루션들이 성능 최적화를 위해 어떠한 기능과 방법을 사용하는지 조사해 보고 싶다.
